# Chargeback Shield

**Razorpay AI Buildathon 2026 -- Track 02, AI Risk Manager**
Loss class: **chargeback / friendly-fraud disputes** (one class of loss, per the track brief).

Chargeback Shield does two things, deliberately kept separate:

1. **Predicts** which transactions are at elevated risk of a future dispute,
   before any dispute is filed -- so a merchant can take a cheap preventive
   step (confirmation email, short settlement hold).
2. **Responds** when a dispute *is* filed: assembles exactly the evidence a
   card network's reason code requires, and recommends fight / concede /
   review under a fixed, auditable policy -- never an LLM guess.

Every score and every packet decision is written to an append-only audit
log (`reports/audit.db`), so any single decision can be inspected after the
fact.

## Why this and not generic fraud detection
Pre-authorization transaction-fraud scoring is a crowded lane (see
`ARCHITECTURE.md` for how this differs from other public buildathon
entries). Chargeback Shield deliberately scores a different point in the
payment lifecycle -- the dispute itself -- and pairs the prediction with an
automated *response*, which is closer to what the track brief actually asks
for ("fraud detection, verification, or automated response systems").

## Honesty about the data
**All data is synthetic**, generated by `src/data_gen.py` from documented
correlates of friendly fraud (digital goods with no delivery confirmation,
cross-border mismatches, subscriptions, oversized first purchases, repeat
disputers) plus noise. It is not fit to, or derived from, any real Razorpay
or cardholder data. Every metric below should be read as a demonstration of
*methodology*, not a claim about real-world performance -- see
`reports/model_card.md` for the full disclaimer and the honest
precision/recall tradeoff curve (a single flattering number is easy to
cherry-pick; the full curve is not).

## Quickstart
```bash
python -m venv .venv && source .venv/bin/activate   # optional
pip install -r requirements.txt

# 1. Generate synthetic data, train the model, write metrics + model card
python -m scripts.train

# 2. Evaluate the evidence-packet engine over the same synthetic disputes
python -m scripts.evaluate_packets

# 3. Run the test suite
pytest -q

# 4. Run the API + dashboard
uvicorn src.api:app --reload
# open http://127.0.0.1:8000/  -- a live dashboard: model metrics, the
# precision/recall tradeoff table, the evidence-packet engine's batch
# results, and interactive forms to score a transaction, generate an
# evidence packet for a sample dispute, and look up its audit record.
#
# Raw JSON API, if you'd rather script against it directly:
# POST /score, POST /disputes/packet, GET /audit/{id}, GET /metrics,
# GET /packet-metrics, GET /sample-disputes
```

## Current results (synthetic, held-out test set)
See `reports/metrics.json`, `reports/model_card.md`, and
`reports/packet_metrics.json` after running the commands above -- they are
regenerated fresh every run, so this README doesn't hardcode numbers that
could go stale.

## Project layout
```
src/
  schemas.py          pydantic contracts (Transaction, Dispute, EvidencePacket, ...)
  data_gen.py          synthetic transaction + dispute generator (ground truth)
  features.py          shared feature engineering (training + live API)
  model.py             HistGradientBoosting risk model, train() + RiskModel
  evidence_engine.py   reason-code -> evidence map, deterministic fight/concede/review policy
  audit.py             append-only SQLite audit trail
  api.py               FastAPI surface
scripts/
  train.py             generate data (if needed) -> train -> metrics.json + model_card.md
  evaluate_packets.py  evidence-engine batch evaluation -> packet_metrics.json
tests/                 pytest suite for the model and the policy engine
reports/               generated: model.joblib, metrics.json, model_card.md, audit.db
```

## Roadmap (not built in v1, on purpose)
- Real evidence-retrieval integration (currently simulated) in place of the
  synthetic evidence store.
- An optional LLM layer purely to draft the packet's human-readable
  narrative from the retrieved evidence -- it would never be allowed to
  decide fight/concede or add evidence the retrieval layer didn't return.
- A small dashboard UI over the existing API.

## Pitch outline (for the 5-minute video)
1. The business lever: chargeback ratio drives real card-network compliance
   risk for merchants, not just the disputed amount.
2. Two-stage system: predict before the dispute, respond after it.
3. Show the honest precision/recall tradeoff table -- not one number.
4. Show one FIGHT and one CONCEDE packet end to end, and the audit record
   behind each.
5. Close on what's deliberately *not* automated (the LLM never decides)
   and why that matters for a defense-only track.
